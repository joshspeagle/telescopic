# M7 review: pools, interrupts, progress

**Diff:** 1b1d66f..8981d31 in `src/` and `tests/`, about 730 lines touching the public
API: three `/simplify` reviewers (DECISIONS #3), on altitude, efficiency, and reuse with
simplification. The `/code-review` follows these fixes.

## Outcome

- **The first Ctrl-C on a pool reaches the workers** (altitude). Cancelling the chunks
  not started could not stop the running ones, which kept refilling their lanes, nor the
  calls `ProcessPoolExecutor` had already queued. An event now tells telescopic's
  workers to start no new replicate, and a chunk that starts afterwards runs nothing,
  except the first. Finished sets on a pool need not be prefixes; the requested indices
  of DECISIONS #20 already handle that.
- **One channel** (altitude). `execute` took an interrupt, a monitor used only in this
  process and an `on_part` used only on pools. The engine's monitor now carries all of
  it: progress, slow pairs, and the stop as its return value. On a pool it sees the
  finished replicates after each chunk and every 0.1 s, through a queue fed by done
  callbacks instead of `wait` over every pending future (efficiency).
- **Slow pairs on a pool** (altitude, reuse). The rule "skip the run-end slow warning
  unless on a pool" left slow pilot pairs on a pool unwarned. `_SlowPairs` now warns
  live from the status and, if it has not, from the meeting times when a run ends, with
  the live condition min(τ, max_iter) > threshold.
- **Workers live for one call** (altitude, efficiency). Each run started and stopped its
  own pool, so `sample` paid twice. An integer pool now opens for one call of `run` or
  `meeting_times`, starts before tuning so that its start overlaps it, and serves the
  pilot and the run. The job (5 KB) travels with each task, so the workers need no job
  at start. A pool kept for the sampler's life would also save the start of later calls
  (1.1 to 1.4 s each) but leaves idle processes and needs a `close`.
- **Chunks of full lanes** (efficiency). Four chunks per worker cut 200 replicates into
  chunks of 13, and 7 lanes cost 17.4 µs per replicate-iteration against 4.5 at 64.
  Chunks now number one per worker at least, more where a chunk would exceed 64 lanes,
  and four per worker at most, cut by `np.array_split` (reuse).
- **Worker settings** (altitude, efficiency). `threadpool_limits(1)` rescanned the
  libraries on every task (2.3 ms); one cached controller limits in 0.01 ms. A task in
  the main thread of another process also ignores Ctrl-C: before, a user's process pool
  returned `KeyboardInterrupt` from its tasks after one Ctrl-C. Tasks in the parent, or
  in other threads, leave both settings alone.
- **Simpler code** (reuse). `Job` was `functools.partial` over `engine.run`;
  `_install`, `_run_installed`, `_run_shipped`, `on_part` and `OnPart` went. `_run`
  derives `store` and the Ctrl-C handling from the namespace. `Interrupt.catching`
  yields nothing. `engine.run` takes indices as an array (`np.fromiter` cost 58 ms at
  10^6), and `_next_indices` uses `assume_unique` (0.8 s to 6.5 ms at 10^6).
- **Tests** (reuse). Mutants showed gaps: the sampler test passed without its pool, the
  pool check was tested apart from the constructor, progress on a pool and bar
  increments were untested, completion asked for exactly the missing replicates, and
  cloudpickle was never used. New tests cover these, Ctrl-C during the pilot (it
  raises), a run in another thread, tasks in this process leaving settings alone, slow
  pilot pairs on a pool, the stop event, the chunk rule and a chunk that starts after
  the stop; `vars` replaces a hand-kept field list. Each fails on its mutant (fifteen
  checked).

Measured on the final code against 8981d31, two interleaved runs each (Intel Xeon @

## Findings not adopted, or deferred

- Efficiency: importing `scipy.stats` at first use in `results.py` would save 0.35 s of
  each worker's start. It is outside the diff, and the start now overlaps tuning; M9's
  benchmarks will weigh it.
- Efficiency: `np.unique` in `merge` costs 0.4 s at 10^6 replicates, under 0.06% of a
  run of that size. It stays.
- Efficiency: waves on pools with only `map` wait for their slowest chunk. A blocking
  `map` has no other place to stop; with chunks of full lanes, runs below 64 replicates
  per worker are one wave.
- Altitude: the size of a user's pool is guessed from `_max_workers` or the CPU count.
  An argument for it is a question for Josh (QUESTIONS).
- Reuse: a test for the parent's wall time on pools and for the clean-up after a worker
  error (terminate, shutdown, cancel). Low value: neither changes a result.
